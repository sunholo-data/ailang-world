## Planner findings — where the design doc is wrong or under-specified

These are the reason to read this plan. Each is first-party measured at base.

**P1 — AC-M1-1 has no named mutation (12 ACs, 11 mutations).** Advisory, not a blocker. Disposition
above.

**P2 — AC-M1-8 is self-contradictory as literally written. BLOCKING if implemented verbatim.**
Its prose says the parser "proceeds to zero-check classification"; its assertion demands `rc=0`. But
the doc's own verdict table maps a classified zero-check commit to **exit 1**. An executor
implementing it as a classification run gets rc=1 and reads correct code as a failure; one
implementing rc=0 appears to contradict the verdict table. **Resolution bound by this plan:**
`--check-runs-file` is a **PARSER-ONLY mode** — it parses one response, prints `total_count=<n>`,
exits 0 on a valid parse and 2 on an invalid one, and performs no classification and no enumeration.
Under that reading AC-M1-7 and AC-M1-8 are both satisfiable and both mutations still kill.

**P3 — the timeout mechanism does not exist on this rig. BLOCKING if implemented verbatim.**
Measured: `command -v timeout` → rc=1 **absent**; `command -v gtimeout` → rc=1 **absent**; and
`gh api --help` (gh 2.99.0) lists **no `--timeout` flag**. Decision 4's "every `gh api` call is
bounded with an explicit timeout" has no off-the-shelf implementation here. Worse, AC-M1-6 as
written cannot discriminate: `--gh-bin /nonexistent/gh` (AC-M1-5) and `--gh-timeout 0.001`
(AC-M1-6) both yield rc=2, so AC-M1-6 could pass on AC-M1-5's mechanism and its mutation survive.
**Planner-measured fix**, a bash-3.2 background+watchdog wrapper (background the child; watchdog
subshell sleeps then `kill -TERM`, then `kill -KILL`; `wait` the child; map rc ≥ 128 to TIMEOUT):

```text
/bin/sleep 3   under 0.05s  -> 124   (timeout)
/bin/echo hello under 5s    -> 0     (output captured)
/nonexistent/gh             -> 127   (unreachable)
sh -c 'exit 7'              -> 7     (real failure)
```

Four distinct outcomes, so TIMEOUT and UNREACHABLE can carry different messages while both exit 2.
The arm must use a stub `gh` that sleeps (offline, deterministic), assert the message names a
timeout, and bound its own wall clock so the unbounded mutant **fails** rather than hangs the suite.
Note the wrapper emits a job-control `Terminated: 15` line on stderr — suppress it, or a controller
reading the Gate-1 report will see it as an error.

**P4 — five ACs are unsatisfiable without a stub-`gh` injection point the doc never names.
BLOCKING as written.** AC-M1-2, AC-M1-3, AC-M1-9, AC-M1-10 and AC-M2-2 all "build a throwaway repo"
and then assert on check counts. Those SHAs do not exist on github.com — the real API returns 404,
not `total_count:2`. Measured: a throwaway repo has no origin remote at all
(`git remote get-url origin` → rc=2, "error: No such remote 'origin'"), so the instrument cannot even
derive the repo slug there. **Fix:** a SHA-keyed stub `gh` passed via `--gh-bin`, plus a `--repo`
flag with an origin-derived default and a loud fail (exit 2) when neither is available. Related: the
instrument must **not** copy `verify_ail.sh`'s `cd "$(dirname "$0")/.."` idiom — that would pin it to
the repo root and make every throwaway-repo arm impossible. Hence `--repo-dir`, default `.`.

**P5 — both CI jobs check out shallow, so no arm may name a SHA of this repository. HIGH RISK.**
Read first-party: `ci.yml` lines 24 and 105 are bare `- uses: actions/checkout@v4` with no
`fetch-depth`, which defaults to **1**. Any arm resolving a real repo range is green on this rig and
red in CI with "Invalid revision range". **Fix:** every arm is self-contained (throwaway repo + stub
gh) and the doc's two real-repo AC commands (AC-M1-5, AC-M1-6) stay developer-run with stub twins in
the suite. Do **not** "fix" this with `fetch-depth: 0` — that slows both jobs for a test that needs
no history. Related: the doc elides AC-M1-5/6's base SHA as `eff748911…`; the full form is
`eff74891141567d63d9ba3bf1cba6ca54b624a54` and the range resolves to 3 commits (2 after head
exclusion).

**P6 — the ~0.15-day estimate is roughly 4× low.** The instrument is the small half. The harness
carries a SHA-keyed stub `gh`, a throwaway-repo builder that must construct a real merge history, a
hand-rolled bounded-subprocess wrapper (P3), a python3 parser with a narrow consistency rule (P8),
six arms plus an `--only` dispatcher with an unknown-arm refusal, three fixtures, and twelve mutation
rows each under a nine-step protocol. 0.15 days is ~1.2 hours; the mutation protocol alone is about
that. Estimate here: **0.5–0.75 day**, still one mission iteration, ~700 insertions — between the
repo's nine-row landed mean (813) and median (1001), i.e. a normal-sized row.

**P7 — nothing in CI syntax-checks bash 3.2 in this workflow.** `ci.yml` at base has exactly **two**
jobs, both ubuntu/bash 5. There is no `launchd drivers (bash 3.2)` job. `/bin/bash` here is
**3.2.57**, and its classic trap — an inline `=~` pattern containing a space or a quote — is a
syntax error that fails in the *fake-a-pass* direction: every input is "rejected", so reject-arms
read green while the parser rejected everything. Any regex in the new scripts must live in a
variable, and `/bin/bash -n` on both scripts is a mandatory local gate at every boundary, read
**before** any mutation result.

**P8 — a naive `total_count == len(check_runs)` consistency rule will falsely loud-fail.** The doc
requires a loud fail when `total_count` is "inconsistent with the `check_runs` array". The endpoint
paginates at 30, so a commit with 50 checks legitimately returns `total_count:50` with 30 entries.
Write the rule one-directional: fail only when (`total_count == 0` **and** `len > 0`) or
(`total_count > 0` **and** `len == 0`). This repo has two jobs so the bug would never show here —
which is exactly why it must be written correctly now.

**P9 — the M1/M2 cut is thin on its report-format half.** M2 is billed as "CI wiring + the report
format", but AC-M1-3 already requires MS1 to emit the per-commit `ZERO-CHECK-CANDIDATE` line. If the
executor defers that line to MS2, AC-M1-3 cannot pass at the MS1 boundary and MS1 stops being
independently green. MS1 therefore ships the final per-commit line; MS2's real content is the exit-1
**summary** wording, the `report` arm, and the CI step. Stated openly rather than dressed up as two
equal halves.

**P10 — AC-M2-1 is a grep and cannot discharge "CI runs the suite".** A step can be present and
never execute (wrong job, wrong indentation, `continue-on-error`). Keep it as a labelled control;
the discharge is the green CI run at the MS2 boundary plus an assertion that `continue-on-error`
appears nowhere in `ci.yml`.

**P11 — a second zsh trap beyond the bash/zsh one.** In this agent's zsh, `grep` is a shell function
resolving to **ugrep 7.8.4**, not GNU grep. Every AC command in this plan that greps uses the
absolute `/usr/bin/grep`, and the instrument must not depend on whatever `grep` is on PATH.

**P12 — AC-M1-10's arm is real and its mutant is genuinely killed, but only if the zero-check goes
on a *second* parent.** Planner built the exact history first-party (`git init`; base; two commits on
main; two commits on a side branch off base; `git merge --no-ff`):
`git rev-list $BASE..$HEAD` → **5** commits; `git rev-list $BASE..$HEAD^` → **2** commits, with
**both** second-parent commits silently dropped. Put the zero-check on a first-parent commit and the
`head^` mutant still surfaces it — the arm goes vacuously green. This is precisely the correction the
doc already records about `e308577` (it survived `head^`; the commit actually dropped was
`725ad5a29`).

**Also re-verified at base, all reproducing:** V10 (`mission-base.sh last gate1` →
`ab5af8c33…`, so the live range *is* empty right now), V12 (pinned binary `AILANG v0.30.0`), V14
(`total_count:2`, 6220 bytes), V15 (`{"total_count":0,"check_runs":[]}`), and the head-exclusion
table on the real range `165b9fd9d..68403eaf5` (5 commits vs 3 under `head^`, with `725ad5a29`
dropped).

**Not measured by the planner:** leg (a) `verify_ail.sh` and leg (b) `go vet`/`go test` were not
re-run this iteration — this sprint adds no `.ail` and no Go file, so both are pure non-regression
controls. **UNMEASURED**; the executor records its own baseline rc for each before touching anything.
