**Premises refined, not reversed.**

- The controller's reading "probes and the archive spend the budget" holds for the clock, but the
  2026-11-03 log shows the clock was gone before any probe ran (claim 2). The design therefore does
  **not** try to give the probes more time under that load. On this rig the probe phase takes
  **4.2–4.8 s** of the 9 s at load 11–13 (V3). The home start's work up to its first probe run took ≥ 9 s; here the same steps up to the probe's
  start take 0.93–0.97 s. That is a slowdown of about 9.3×. It is an estimate: the home figure also
  holds the probe's scratch setup, which this rig did not time separately (§6 R8). At that slowdown no bound that fits inside
  `service start`'s 30 s wait lets five profiles probe (4.2 s × 9.3 ≈ 39 s). What this row can do is
  keep the daemon up, keep the profiles out (fail-closed), and say so in `doctor`.
- On this rig, even at load ~12, a start that must archive both pinned binaries fresh uses
  **8.0 s** of the 9 s clock, leaving 1.05 s. Warm starts use 5.3–5.6 s (V3). So the shared clock was
  close to failing well below the row's load.

## 2. The mechanism being changed

At `61a8d1c4`, `ailang-worldd serve` builds the daemon in one call (V1, V3):

1. `Run` → `startBounded(ctx, cfg, 9 s, New)`. One startup clock starts here.
2. `New`: `MigrateCredentials(ctx)`, `store.Open`, and the tool binary's archive (`archiveToolBinary`).
   The archive copies and hashes about 100 MB and takes no ctx (`archive.go:225`, `:278`).
3. `configureRunCaps(ctx)`, which is a no-op on the home service (no `--run-*` flag).
4. `configureExec(ctx)` → `broker.StartExec(ctx, …)`:
   - `node --version`, which is ctx-bounded;
   - the srt tree, then `ArchiveExecSandbox`, which takes no ctx;
   - `ProbeExecProfilesEach`, which probes every profile at once. Each probe run's budget is
     `min(execProbeRunBudget = 8 s, time left on ctx)`. A run that starts with nothing left returns
     `the startup budget is spent` (`exec_probe.go:396–402`).
   - `applyProbe`: a failed `--exec-profile` refuses startup. A failed directory profile is left out
     with `errs[i].Error()` as its reason (`exec_startup.go:256`, `:264–265`).
5. The interpreter's archive, about 100 MB, with no ctx (`daemon.go:830`).
6. `bootstrapRegistry(ctx)` on the **same** ctx. If it is past its deadline,
   `abortBudget(StageRegistry)` follows, then `daemon startup failed at registry-bootstrap: …
   context deadline exceeded`, and `serve` exits.
7. `reportTemplates(ctx)` and `scanIntegrity(ctx)` also run on the same ctx.

`service start` then polls `/v1/health` for 30 s (`service.go:87`, `:240`). It stops the service
when nothing answers: `build did not answer /v1/health within 30 s; service stopped` (`:256`).
The plist has `KeepAlive` and `ThrottleInterval 30` (V1 P11), so launchd cannot relaunch inside
that window.

**Reproduced with no host load** (V4, the positive control). A probe client that never answers
stands in for the load. In a `git archive 61a8d1c4` copy, a throwaway test built HEAD's own shape,
`startBounded(ctx, cfg, 1.5 s, New)`, with one directory profile:
`daemon startup failed at registry-bootstrap: cannot bootstrap world/epoch-registry/v1 with release
"unpinned": context deadline exceeded` after 1.91 s, and the log shows `left out: exec startup probe
failed … (7 of 7 arms)`. HEAD's real `Run` (9 s) failed the same way after 9.21 s. The control, the
same rig with an answering client and the 9 s clock, started in 2.50 s, with the profile left out by
its arms.

## 3. Design

### 3.1 What this row builds, per candidate

| Candidate | Decision | Why (measured) |
|---|---|---|
| (1) The registry bootstrap gets its own deadline | **BUILT.** It covers the whole *registry phase* (bootstrap, template report, integrity sweep), §3.2 | The bootstrap itself takes 0–2 ms on this rig (V3). Only the shared clock made it fail. The template report and the sweep run on the same ctx after it, so a fresh clock for the bootstrap alone would leave the sweep on a spent clock. The sweep then reports a false `scan` hole, which `MUT-SWEEP-ON-STARTUP-CLOCK` shows (§5) |
| (2) Retry a profile whose probe ran out of time | **NARROWED.** The probe now tells "ran out of time" from "an arm refused" (§3.3), and `/v1/health`, the log and `doctor` all say which it was. **No retry loop.** The loop is proposed as a follow-on row (§9) | A post-startup re-probe would have to make the startup exec state mutable. Today 10 functions read it and **no lock guards it** (`mu` guards `handler`/`ailangBuild`, `execMu` guards `execH`). `ExecToolState` also captures the profile set once, when it is built (`exec_tools.go:148`, `:161`) (V6). That is a concurrency change to the fail-closed gate's state, with a different correctness bar from the clock split. Recent rounds blocked docs that bundled two such bars. And at the row's load a retry would not have helped soon: the probe phase needs about 4.2–4.8 s × 9.3 (§1) |
| (3) Name left-out profiles in `/v1/health` and in `doctor` | **BUILT for `doctor`.** `/v1/health` already had them; it gains `out_of_time` (§3.4) | V1 P7, P8 |
| (4) An exec call for a left-out profile refuses with its name | **ALREADY BUILT** (row 189). Nothing is built; T2 pins the path from a load-left-out profile | §1 claim 4 |

### 3.2 Two startup clocks, both bounded

`Run` now calls `startDaemon(ctx, cfg, startupBudget, registryPhaseBudget)` (`daemon.go:1322–1330`,
patched):

- **The startup clock**, `startupBudget = 9 s`, is HEAD's constant and value, unchanged. It is still
  made by `startBounded`. It bounds `New` up to and including the exec probe and the interpreter
  archive.
- **The registry clock**, `registryPhaseBudget = 9 s`, is new. `newDaemon` starts it from serve's
  own ctx (`phaseParent`) at the moment the registry phase starts:
  `regCtx, cancelReg := context.WithTimeout(phaseParent, registryBudget)` (`:879`).
  `bootstrapRegistry`, `reportTemplates` and `scanIntegrity` take `regCtx` (`:886–894`). Nothing
  before it shares it, so it never inherits time the probes, or the work in front of them, spent.
- `New(ctx, cfg)` keeps its signature for its 47 test call sites, as
  `newDaemon(ctx, ctx, registryPhaseBudget, cfg)`. When there is no separate parent, the registry
  clock is the smaller of the caller's deadline and 9 s.
- No new context root. Both clocks derive from serve's ctx with `WithTimeout`, so the
  context-root census (`TestProductionContextRoots`) is unchanged and green (§5).

**Why 9 s for the registry clock.**

- The value is the existing startup constant (`daemon.go:1284`). The bootstrap never gets less than
  HEAD gave it when nothing before it was slow.
- The measured stimulus is small: bootstrap 0–2 ms, template report 8–19 ms, sweep 2–7 ms (V3). At
  the ~9.3× slowdown of §1 that is ≤ 0.3 s, so the clock exists to bound a wedged store or a
  SQLite lock wait, not the normal work.
- A smaller existing constant, `commitBudget` (3 s, B6), would not fit: the sweep alone may use
  `integrityScanTimeBudget` (2 s) plus one page read. A sweep cut short by the clock reports a
  false hole (§3.1).

**Accounting against `service start`'s 30 s.**

- The two clocks bound the ctx-aware work at 9 s + 9 s = 18 s.
- The ctx-free work is the three archives. Warm, they took 216–245 ms (tool binary), 276–331 ms
  (srt) and 132–171 ms (interpreter) on this rig, 0.62–0.75 s in all (V3).
- The two archives in front of the probe run inside the startup clock's wall time. The
  interpreter's runs after the probe and before the registry clock.
- At the ~9.3× slowdown, a warm start is therefore about 9 s (startup clock, spent) +
  0.17 s × 9.3 ≈ 1.6 s (interpreter archive) + ≤ 0.3 s (registry phase) ≈ 11 s. That is inside the
  30 s wait.
- The worst case, with the registry clock fully used on a wedged store, is about 20 s, still inside.
- A **cold** start (both binaries archived fresh) took 2.76 s of ctx-free work at load ~12. At 9.3×
  that alone exceeds 30 s. This row does not fix that case (§6 R2).

### 3.3 "Out of time" is told apart from "an arm refused"

- `execProber` gains `deadline` (`exec_probe.go:443`). `probeExecProfile` sets it from the startup
  ctx (`:499`).
- `fail` marks a failed arm `spent` when it is judged at or after that deadline (`:447`).
- `ExecProbeError.OutOfTime()` (`:245`) is true only when **every** failed arm is `spent`. One arm
  that failed while time remained makes it false.
- `applyProbe` copies it into `ExecProfileExclusion.OutOfTime` (`exec_startup.go:269–271`).
- The profile is deleted from the served set exactly as before (`:272`). The flag is written only
  into the exclusion.

This is conservative in one direction: when in doubt, it says "an arm refused".

- A probe run that hits its **own** 8 s per-run bound while startup time remains is judged in time,
  so it counts as an arm failure. HEAD's `Run` reproduction shows that case: arm 1 reads `timed out
  after 8s` (V4), and §6 R3 covers it.
- A genuine refusal judged after the deadline would be marked out of time. That can only happen to
  a run that finished within a few milliseconds of the deadline. It changes only the advice; the
  profile is still left out.

The name avoids "budget". Row 255 already owns the exec-call class `time-budget-spent`, and the
broker owns `denied:budget`.

### 3.4 Where an operator sees it

- **Log** (`workspace.go:270`). The existing `exec profile "<p>" (<file>) left out: <reason>` line is
  unchanged. For an out-of-time profile one more line follows: `exec profile "<p>": its startup probe
  ran out of startup time (every failed arm was judged after the startup clock ran out: host load);
  restart serve when the host is quieter`.
- **`/v1/health`**. `exec_profiles_excluded[]` gains `"out_of_time": true`, tagged `omitempty`, so
  every other health body keeps its bytes. The change is additive, as `HealthResponse`'s doc requires
  (`daemon.go:610`).
- **`doctor`** (`doctor.go:344`, `:352`). `doctorDaemon` already decodes `/v1/health`. It now also
  decodes `exec_profiles_excluded` and, after its ✓ line, writes one **✗ `exec profiles`** line per
  left-out profile, naming the project, the file and the reason (one line, 240 bytes).
  - The fix for an out-of-time profile is a restart once the host is quieter.
  - Any other profile is told to fix its file.
  - `exec profiles` joins the exec class (exit 13) in `doctorClass`.
  - Because `doctorDaemon` always runs, `--quick` shows these lines too: the row's "doctor was all
    green" case.
  - `doctor --help` lists the check.
- **The refusal** an agent gets is unchanged (candidate 4): `exec profile "<p>" of episode "<e>" was
  left out at serve startup: <reason>`.
- **Docs (S7)**: one `docs/QUICKSTART.md` sentence block where the profiles directory is introduced.

### 3.5 Fail-closed

No path serves a profile whose probe did not pass every arm. The served set is `st.Profiles` after
`applyProbe`. `applyProbe` deletes every profile with a non-nil probe result, whatever `OutOfTime`
says. The flag is written only into `st.Excluded` and never reaches `st.Profiles` (§4 Claim C).

The registry clock changes when the daemon gives up, never what it serves. A flagged
`--exec-profile` whose probe runs out of time still refuses startup, as any failed `--exec-profile`
does (T4's last row).

### 3.6 Pure core, and why this is not a package

This is Go host code: the daemon's startup and the probe's bookkeeping. **No `.ail` is touched**,
and S1's Z3 contracts bind `world/` and `.ail` code. `OutOfTime` and `fail`'s rule are pure
functions of their inputs and the clock reading, and T4 tests them with no process run. A package
cannot hold this, because it is the host boundary's own startup (S2, S3).

## 4. The by-construction argument

**Claim A (serve's registry phase never inherits the startup clock).** *Proof.*

- `Run` calls `startDaemon(ctx, …)` (`daemon.go:1330`). `startDaemon` passes `ctx` as `phaseParent`
  and the startup clock as `ctx` to `newDaemon` (`:1324`).
- `regCtx` is `WithTimeout(phaseParent, registryBudget)` (`:879`).
- The three registry-phase calls take `regCtx` and nothing else (`:886`, `:892`, `:894`).

∎ T1 (`Serve`, through `Run`) kills `MUT-RUN-HEAD-SHAPE`. T1 and T2 (`Phase`) kill
`MUT-SHARED-PARENT`. T2 kills `MUT-SWEEP-ON-STARTUP-CLOCK`.

**Claim B (every clock is bounded).** *Proof.*

- The startup clock is `startBounded`'s `WithTimeout`, unchanged.
- The registry clock is `WithTimeout(phaseParent, registryBudget)`.
- Both values are 9 s, pinned by T6 (`Pin`).

∎ T3 (`Bound`) runs the registry clock at 1 ns and gets `registry-bootstrap … context deadline
exceeded`, which kills `MUT-REGISTRY-UNBOUNDED`. T6 kills both budget mutants.

**Claim C (fail-closed: a profile whose probe did not pass is never served).** *Proof.*

- In `applyProbe` every `i` with `errs[i] != nil` reaches `delete(st.Profiles, p.Project)`
  (`exec_startup.go:272`) unconditionally.
- `OutOfTime` is computed above that line and written only into `st.Excluded`.
- `w.exec.byProject` is `st.Profiles` (`workspace.go:260`).
- `profileFor` refuses any project in `excludedWhy` before it reads `byProject` (`:194–197`).

∎ T4 (`Spent`), T1 and T2 kill `MUT-SERVE-SPENT` (an out-of-time profile is skipped, so it stays
served) and `MUT-SPENT-STILL-SERVED` (it is left out but not deleted).

**Claim D (`out_of_time` never names an in-time refusal as load).** *Proof.* `OutOfTime()` returns
false as soon as one failed arm is not `spent`, and false when nothing failed. ∎ T4's truth table
kills `MUT-SPENT-ANY`. T1 and T2 kill `MUT-FAIL-NEVER-SPENT`, `MUT-DEADLINE-UNSET`,
`MUT-FLAG-NOT-CARRIED` and `MUT-HEALTH-DROPS-FLAG`. T2's control row (an answering client, real
arm refusals) expects `out_of_time` false.

**Claim E (doctor names every left-out profile as an exec failure).** *Proof.* `doctorExecProfiles`
calls `r.add(markFail, "exec profiles", …)` once for each element of `exec_profiles_excluded`, and
`doctorClass("exec profiles")` is `("exec", 13)`. ∎ T5 (`Doctor`) kills `MUT-DOCTOR-NOT-CALLED`,
`MUT-DOCTOR-WARN`, `MUT-DOCTOR-CLASS` and `MUT-DOCTOR-ONE-FIX`.

**Claim F (neighbours untouched).** *Proof.* The patch's file list (V16) contains none of row 255's
files (`failure.go`, `record.go`, `broker.go`, `handlers_exec.go`, `effectful.go`, `why.go`,
`mcpclient.go`, `projection.go`). In `exec_probe.go` it changes only `ExecProbeArmFailure`,
`ExecProbeError.OutOfTime`, `execProber.deadline`, `fail` and two lines in `probeExecProfile`. No
verdict (`judgeReverse`, `judgeLeg`, `net6Leg`, `reverseLeg`, `classify*`) reads `deadline` or
`spent`. ∎ The existing probe tests stay green in the full broker package (V12).

## 6. Residuals and risks

- **R1, no retry: a profile left out by load stays out until a restart.**
  - Under sustained load the daemon now comes up, exec stays down for that project, and `doctor`
    says so with the restart fix.
  - The automatic re-probe is the follow-on row in §9, with V6's surface (10 reader functions,
    0 locks, `ExecToolState` captured once) as its premise.
- **R2, a cold start under very heavy load can still miss the 30 s wait.** The three archives took
  2.76 s cold at load ~12 (V3). At the ~9.3× slowdown that alone exceeds 30 s. The archives take no
  ctx (`archive.go:225`), and this row does not move them. A cold archive happens only when a pinned
  binary changes (`setup --replace`), not on a `service upgrade` of `ailang-worldd` itself.
- **R3, a probe run that hits its own 8 s bound is reported as an arm failure.** In HEAD's 9 s
  reproduction, arm 1 read `timed out after 8s` with about 1 s of the startup clock left (V4). Such a
  profile is left out with `out_of_time: false`, and `doctor` tells the operator to fix the file. The
  reason text still says `timed out after 8s`. This errs toward investigation, never toward serving.
- **R4, a flagged `--exec-profile` that runs out of time still refuses startup**, as at HEAD. That
  is the operator's explicit single-profile flag. The home service uses `--exec-profiles-dir`
  (V1 P11).
- **R5, a wedged store now takes up to 9 s longer to refuse startup**, because the registry clock is
  fresh. This is inside the 30 s wait (§3.2).
- **R6, `MUT-TEMPLATES-ON-STARTUP-CLOCK` survives.** No daemon rig archives an interpreter. The code
  is one argument in the same three-line block whose sweep line `MUT-SWEEP-ON-STARTUP-CLOCK` pins.
- **R7, Linux (UNMEASURED).** T1 and T2 use the existing pass-through srt shim and a `/bin/sh`
  client, as the row-140 refusal table does. They run in CI's plain `go test ./...` leg on Linux,
  which is the acceptance gate (§7).
- **R8, the load stand-in certifies one axis.** A client that never answers makes the probe phase
  spend the clock, which is the 2026-11-03 mechanism (V4). It does not reproduce CPU or I/O
  contention on the other steps. The ×9.3 figure is an estimate from one logged instance (§1 claim 2). The
  rig's timings are from a shared host at load 7–13.
